# v1 保持模擬決定性、輸入可錄製——為計畫中的 v2 素材工具鋪路

即使 v1 沒有錄製／重播功能，仍要求：(1) 模擬結果**同機可重現**——固定時間步、不讀 wall-clock，且**網格生成用有種子的亂數**（種子 = hash(圖片位元組 + 網格參數)），同一張圖 + 同參數永遠得到同一個 Sim mesh；(2) 所有會影響模擬的輸入收斂到單一窄介面 `applyInput(event)`（`event` ∈ grab / moveGrab / pin / unpin / movePin / tap / release / cameraMove）。**v1 不做**錄製器、序列化格式、時間軸。

## 為什麼

v2 規劃一個「素材工具」：使用者錄製多段獨立操作（每段一條 Track），各設起始時間、疊加播放，連同相機操作一起，產生想要的效果片段。它要能**精確重播**，否則錄好的片段每次跑都不一樣。

這對 v1 是兩個看不見的約束：
- **決定性**：目前 prototype 撒內部點用 `Math.random`——同一張圖每次重載網格都不同，重播不可能精確。換成種子亂數約 10 行，而且非決定性網格本身就是潛在 bug（重載後手感微妙不同）。
- **輸入可攔截**：若即時輸入層直接呼叫求解器，未來要加錄製器就得動很多地方。先把所有輸入走 `applyInput(event)`，即時層與 Demo 都走它，未來的錄製器包在外面即可。

不記下來的話，未來有人會把種子亂數「簡化」掉、或讓輸入層繞過介面直接操作求解器。

## Considered Options

- **v1 完全不管，v2 再重構**：v2 要回頭把決定性與輸入攔截補進已成形的程式，成本高且容易漏。現在鋪幾乎零成本。
- **v1 就把 Track 資料格式與時間軸定好**：在知道工具長怎樣之前定格式，多半白做。內建 Demo 先用程式碼寫（走同一個 `applyInput`）。

## Consequences

- 跨機器／跨瀏覽器 bit 完全一致**不在 v1 範圍**。v2 的分享大概是「本機把片段算成影片、分享影片」，所以跨平台浮點精確度不會變成關鍵路徑。
- Demo 以程式碼撰寫，但必須透過 `applyInput` 驅動，不得走捷徑。
