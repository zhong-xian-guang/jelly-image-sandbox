# V2 素材工具：相機獨立成軌、錄製拆軌、加入頭尾修剪

（承 ADR-0006）V2 素材工具改為：一次錄製依「錄製目標」（只錄動作／只錄運鏡／兩者同時）產出**動作軌**與／或**相機軌**兩種 Track。相機不再混進動作的輸入流，而是自成一條或多條**相機軌**——每條自帶錄製當下的鏡頭快照，播放到其起始時間即**硬切**進場、再放它自己的相對位移量。相機軌之間在時間軸上不得重疊（軟警告，重疊區間只認先列那條）；動作軌之間可自由重疊（Multi-grab）。每條 Track 增加「頭尾修剪」（track 本地時間的 in／out 數字欄位）。播放加入「從頭播 + 暫停（全凍結：物理、秒數、鏡頭、事件全停）+ 目前秒數顯示」，**不做** scrub／seek，**不做**視覺化時間軸。

## 為什麼

實作 ADR-0006 的混合模型（一條 Track = 指標＋相機的單一輸入流）後，實際使用暴露三個問題：

- 使用者要分開錄「只做動作」與「只運鏡」的段落，但一次錄製難免混入另一種輸入；混合模型下這些雜訊會進到同一條 Track。
- 相機指令是相對位移量。多條各自從不同鏡頭位置錄下的 Track 疊加播放時，位移量套用的起點不明確（取最早那條？相加？），鏡頭會拍錯。
- 使用者的實際剪輯流程是「這段運鏡給 0–2 秒、下一段給 2–4 秒」的分段鏡頭，還要能錄鬆一點再修頭尾——ADR-0006 都沒有。

把相機獨立成軌、每條相機軌自我錨定（自帶起點快照 + 硬切），配合「相機軌不重疊」，就保證任何時刻最多一條相機軌絕對掌控鏡頭，起點永遠明確。錄製拆軌讓「只錄動作」的 take 天然不含相機雜訊。頭尾修剪用兩個數字欄位即可，不必畫時間軸。

## Considered Options

- **維持 ADR-0006 混合模型 + 疊加時取最早那條的鏡頭起點**：實作簡單，但多段運鏡疊加時鏡頭起點不明確、會拍錯，也無法乾淨分離「只錄動作」與「只運鏡」。
- **相機指令改記絕對鏡頭狀態（keyframe）而非相對位移**：起點不再有歧義，但兩條相機軌重疊時「哪個絕對值生效」又變成新問題，且與現有 `updateCamera` 的即時平滑模型衝突。
- **視覺化多軌時間軸（ADR-0006 已推遲的那種）**：更好操作，但畫 timeline canvas + 拖曳成本高，兩個數字欄位就能滿足分段與修剪。

## Consequences

- ADR-0006 的「錄一條輸入事件流（含相機操作）」與「只能整條刪除重錄、不做頭尾修剪」兩點作廢；其餘（不內建影片匯出、用 OBS、不做視覺化時間軸／波形、不管跨機器 bit 一致）仍成立。
- `#28` spec 需重寫（US2 相機錄進同一條 Track、Implementation Decisions 的「一條 Track = 聯集」、Out of Scope 的「不做修剪頭尾」）。`#29`（已 merge）的單一混合 Track 產出要改成拆軌；`#30` 的 commit 作廢（`mergeTracks`／`PointerId` 前綴邏輯留作實作參考，仍適用於動作軌之間的疊加）；`#31` 併入重切票。
- 「相鄰相機軌平滑銜接」（播放到下一段不硬切、改從當前鏡頭位置接續）列為每條相機軌之後可加的選項，這版不做。

## 追記（2026-09-07）：片段初始 Pin

實作 `#33`（多動作軌）後，錄「Pin 效果」的 use case 暴露一個洞：`播放全部` 為了決定性一定要 `sim.reset()`（錄下的絕對世界座標要落在 rest 形狀上），於是事前手動擺好的 Pin 會被清掉；但把「放 Pin」整段錄進 Action Track，又會讓每次播放都得重看十幾秒的擺放過程。

決定：**片段可帶一份「初始 Pin」快照**，獨立於任何 Track。使用者擺好 Pin 後明確按鈕拍下；`播放全部` 在 `sim.reset()` 之後、跑合併時間軸之前，於 step 0 一次還原，再照常播放。這是本 ADR「每片段自我錨定、播放前場景被怎麼動過都不影響重播」論點延伸到第三種狀態——前兩種是動作座標靠 `sim.reset()` 對齊、相機靠 `startCamera` 硬切，Pin 則靠初始快照 step-0 還原。

- **相對其他選項**：「`播放全部` 不重設 Pin、把 Pin 當活場景狀態」實作最省，但「活狀態」與「決定性重播」天生打架（兩次播放之間動到 Pin 就變、`停止／重設` 會清掉）；「把錄進軌的 pin 事件在疊加時壓到軌起點」則是 magic、錄下的時序被默默丟掉、且仍得完整錄一次擺放。初始快照多一塊 UI 與狀態，換來片段能完整、決定性重現。
- **形狀**：快照存附著點在 **rest 形狀**下的世界座標（不隨拍快照當下的變形而偏）；`pin` 事件維持 `{x,y}`，只在 `SimCore` 加一個唯讀查詢。疊加時把初始 Pin 組成一條合成 `OverlayTrack`（`startStep: 0`、`idPrefix: 'setup/'`、一串 `atStep: 0` 的 `pin` 事件）排在最前面，`mergeTracks` 不改。
- **與錄進軌的 `pin` 並存**：初始 Pin 是從第 0 秒就在的**佈景**；錄進 Action Track 的 `pin` 是某秒才出現的**效果**。兩者獨立，冗餘（同一表面點各一個）不特判。
- **生命週期**：隨片段保存——`停止／重設` 保留、重新匯入 PNG 清空（比照 Track 清單）。
- **落點**：本節之外不改 ADR-0007 其餘結論。實作為 `#33` 的兄弟票（`#39`），`#38`（場景狀態整合）在其「保留／清空」規則裡引用它。

## 追記（2026-09-09）：可錄的「清除所有 Pin」

實作 `#39`（片段初始 Pin）後，錄「Pin 效果」的下一個 use case——「撐住果凍一段時間 → 全部鬆開 → 看它彈回」——暴露一個洞：控制面板的「清除所有 Pin」按鈕接的是 `SimCore.clearPins()` 直呼，**完全不經** `applyInput`，`TrackRecorder` 攔不到；而且逐一點掉個別 Pin 也沒用——`mergeTracks` 給每條 Action Track 自己的 `PointerId` 前綴（`t1/`、`t2/`…），一條軌的 `unpin` 永遠打不到別條軌（或 `setup/`）放的 Pin（那正是本 ADR 讓「軌之間互不干擾」的機制）。

決定：**新增一個無 `id` 的輸入事件 `{ type: 'clearPins' }`，錄進 Action Track**。重播到該 step 時清掉**畫面上所有 Pin**——所有動作軌放的、以及片段初始 Pin，全部清掉。

- **刻意跨軌**：這與 `#28` User Story 10「軌之間互不干擾（某條的 release 不該連帶放掉另一條的 Grab）」表面衝突，但 US10 針對的是**意外**干擾（id 碰巧撞上）。`clearPins` 是使用者**明確錄下**的動作，「把畫面清乾淨」就是意圖；也忠實對應那顆按鈕本來的行為（它一直都是清全部）。片段初始 Pin 一起被清也是預期內——`#39` 的「β=1 拔不掉」指的是物理甩不掉，不是「沒有任何事件能移除」。
- **相對其他選項**：「只清這條軌自己放的 Pin」能守住 US10（實作上錄製當下把 `sim.listPins()` 展開成一串 `unpin` 即可，前綴天然只命中同軌），但與「把按鈕行為錄下來」的訴求不符，且群組比較時「A 軌清除、B 軌 Pin 保留」這種需求目前沒有；真的需要時再開票。「做成片段層級的排定清除」（對稱於片段初始 Pin、控制面板自己一列、step 可編輯）是另一套 UI，同樣不符合「在一次 take 裡被捕捉」。
- **形狀**：`clearPins` 進 `SimCore.applyInput` 聯集（`SimCore.clearPins()` 本來就是 public method，這只是也讓它走窄介面、順手把 `onClearPins` 繞過 `applyInput` 的直呼拿掉，回到 ADR-0005）。不夾帶「清掉了哪些」的快照——決定性重播，到那個 step 畫面上有什麼就清什麼。`mergeTracks` **零改動**：無 `id` 事件本來就原樣通過、跟著軌的 `startStep` + 頭尾修剪走（比照 `tap`）。`isCameraCommand` 為 false → `DemoRunner` 派給 `applyInput`；`TrackRecorder.stop()` 分流時落 `action` 份 → 錄製目標為「只錄運鏡」時自動不錄。
- **不可編輯性**：就是軌裡的一個事件，受該軌起始秒數 + 頭尾修剪支配，沒有單獨調時間／刪單一個（比照 `#28` Out of Scope）。
- **落點**：本節之外不改 ADR-0007 其餘結論。實作為 `#33` 的兄弟票（`#39` 之後的第二張），`#28` 傘票等 `#39` + 本票都 merge 才關。
